# File02 V12.3 / T24 / NFR-004 — Staging Performance Measurement Protocol

**Status at authoring:** offline tooling available, **ZERO actual staging/field samples**, **NO p75/p95 acceptance**, no user-data or network collection by this tool.

## Measurement provenance
Governed by `Sabri-Website-Master-Plan-V12.3.docx`, File02 `F02-NFR-004`, and `File02-V12.3-Comprehensive-Execution-Plan-v1.0.docx`, T24. The global V12.3 laboratory guidance calls for named device/network profiles, cold/warm caching, at least three repeated runs, route scope and honest field sample handling. Core Web Vitals field p75 requires an independently qualified device/window/URL-or-origin measurement. A small disposable WordPress CI test is **not** a production latency benchmark.

## Offline tool
`tools/file02-staging-latency-analyzer.py` only reads a **privacy-minimized CSV**, makes no HTTP/network requests, does not read WordPress DB and cannot produce a live acceptance receipt. Its default analysis threshold is **100 successful requests per exact grouped staging profile**; this is a *tool quality gate*, **not** an approved service-level target and **not** a Web Vitals field sample count. An approved lab p95 budget requires a distinct owner-approved JSON file; absent approval always yields `no_approved_budget`. HTTP 4xx/5xx in a positive journey yields `http_failures_need_review`, never a green report.

### Only accepted CSV columns, in exact order
```csv
timestamp_utc,route,device_class,network_profile,cache_state,http_status,elapsed_ms
2026-11-14T10:00:00Z,login,mobile_low,slow4g,cold,200,180.0
2026-11-14T10:00:01Z,account_safety,mobile_low,slow4g,warm,200,145.2
```
Never enter full URLs, query strings, cookies, user IDs, email addresses, IP addresses, device IDs, patient data or raw referrers into route/profile labels. Use opaque approved route identifiers only. The input is limited in size; the output contains only group quantiles, counts and the time window.

### Example commands (operator supplies sanitized inputs; NOT RUN)
```bash
python3 tools/file02-staging-latency-analyzer.py PRIVATE_STAGING_SAMPLES.csv \
  --min-samples 100 > PRIVATE_LAB_SUMMARY.json
python3 tools/file02-staging-latency-analyzer.py PRIVATE_STAGING_SAMPLES.csv \
  --approved-budget APPROVED_FILE24_ROUTE_BUDGETS.json \
  > PRIVATE_LAB_SUMMARY_WITH_GATES.json
```

### Explicitly approved budget schema (example only; not a real approval)
```json
{
  "schema": "file02.v12.3.staging-approved-budgets.v1",
  "approved": true,
  "approval_owner": "file24",
  "route_p95_ms": {"login": 500}
}
```
**IMPORTANT:** The number 500 in this example is illustrative, not a V12.3 File02 signed performance limit, and setting `approved:true` in a JSON fixture does not create an external approval. A real operator must separately identify the reviewer, source budget, dates, environment and signed authorization. Do not use this sample as a gate without approval.

## Acceptance must establish
1. Test the **exact reviewed package** on staging, not only repository source. Freeze File00/02/24, WP/PHP/DB, enabled providers and digest.
2. Capture ≥3 repeated cold/warm runs per supported device/network/route profile. Use adequate additional samples when proposing statistical quantiles; mark low sample `insufficient_sample`.
3. Report measured latency, HTTP failure counts, query/provider duration where legitimately safe, and a versioned approved route-specific target. Never mix positive login with intentional rejection cases.
4. Analyze real Core Web Vitals separately with actual 28-day window, device class, URL/origin scope and adequate data provenance. `field_core_web_vitals=NOT_MEASURED` in this tool is permanent by design.
5. Staging owner and independent File24 QA approve or reject; full browser a11y/RTL, real providers and deployment parity are different gates.

**Release state:** T24 remains **NOT VERIFIED** until actual staging inputs and authorized acceptance exist; a source CI PASS only proves the analyzer behaves as specified.
