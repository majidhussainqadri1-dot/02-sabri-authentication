# R318 — Routes, UI, Templates and Accessibility Review

Review baseline: `033b345acc7ccd405016b9f94dfa196e4c924f83`.

Method: canonical routes, access/private headers, security redirect helpers, login/signup/recovery/Google/profile templates, front-end passkey JavaScript, authentication CSS, admin settings UI and existing route/UI regression coverage were reviewed completely before correction. The defect ledger was then frozen and corrected as a batch.

Defects found:
1. Passive login and Google-account rendering still called mutating `allow_request('google')`, consuming the provider half-open probe that R314 reserved for the actual outbound HTTP request.
2. The canonical `/account/sessions/` unauthenticated redirect pre-encoded its return URL with `rawurlencode()` before passing it to `add_query_arg()`, risking double-encoding and loss of the intended post-login destination.
3. Visible text actions such as Forgot Password, bottom links and `.sa-text-link` did not have the project 44px touch-target gate even though button and checkbox targets did.
4. The Google account page asserted that Google was administrator-disabled whenever `google_ready` was false, even though Safe Mode or provider health could also be the cause.

Corrections: use the non-mutating provider-health projection for passive rendering; remove pre-encoding from the canonical return URL; extend the 44px target gate to text actions; make Google unavailability copy evidence-honest; add `tests/r318-route-ui-hardening-regression.php`.

Correction workflow run: `31811672516` — correction and cumulative regression succeeded. Product correction commit: `17b72901040ca0adac31b0ddeb2aa9baaebde862`.
